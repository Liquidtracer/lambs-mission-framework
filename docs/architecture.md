# LAMBS Mission Framework – architecture and project context

LMF 2.0.0 in `LMF_DEV.Altis`. This document describes technical architecture, module contracts and lasting project context. Code/config describes the implementation; user requirements and agreed design choices describe the intent. Development standards are in [development.md](development.md), AI/Codex instructions in [AGENTS.md](../AGENTS.md) and practical calls in [mission-maker-reference.md](mission-maker-reference.md). Code and settings paths in this document are relative to the mission root.

Read **Common project context** before technical work, then the relevant module sections and dependencies in the index. Read the entire document for a broad review or unclear scope. This overview does not replace inspection of the affected code.

**Agreed boundary – Forward Deploy:** The system is retained only for backward compatibility for mission makers who wish to use it. It must not be assessed, reviewed or changed unless the user explicitly requests work on Forward Deploy. This also applies to general LMF surveys, bug reviews and improvement proposals. The existing description is retained as a reference, not as a list of follow-up work. This boundary applies to Forward Deploy, not the shared Paradrop module.

**Agreed boundary – Vehicle Service:** The component is retained, but according to the mission maker it is practically unused. It must not be assessed, reviewed or changed unless the user explicitly requests work on Vehicle Service. This also applies to general LMF surveys, bug reviews and improvement proposals. The existing description is retained as a reference, not as a list of follow-up work. This boundary applies to `framework/vehicleService/`, not other vehicle initialization or asset spawners.

**Evidence:** The descriptions are based on the static survey dated 2026-09-23 and previously documented source/test experience. The documentation editing is not a new full engine, parser or in-game verification. The development mission is reported to have started successfully after repository preparation. Dedicated/JIP behavior has prior reported runtime validation, but has not been regression-tested again specifically after preparation. This does not confirm that all module-specific edge cases have been tested; specific limitations below are retained. Installed mod versions have not been established. “Design” means agreed intent, “Implementation” describes code, “Observation” means reported runtime behavior and “Unresolved” identifies a specific limitation or missing verification. Unlabeled technical descriptions indicate the implementation, not test evidence. Source links are the previous basis; check relevant current documentation when drawing technical conclusions.

## Common project context

### Layers, structure and interfaces

- `framework/`: reusable LMF code, organized by system. Folders do not indicate execution context; guards, initialization points and contracts determine this.
- `settings/`: LMF configuration for mission makers. See the settings table below.
- `description.ext`: the LMF portions register CfgFunctions, XEH, object sorting and notifications and must accompany the framework when transferred. The rest is mission setup.
- `init.sqf`, `initServer.sqf`, `initPlayerLocal.sqf`, `onFlare.sqs` and Eden are mission integration. `initPlayerLocal.sqf` contains only comments and is an available integration point.
- `mission.sqm` is intentionally stored unbinarized as version-controlled Eden output. Agents may read and inspect the file, including Eden names, init fields, triggers and module synchronization. The file must never be edited directly; changes are made only through Eden Editor.

Function names are `lmf_<system>_fnc_<handling>`. Registered function classes match `fn_<handling>.sqf`; subfolders do not change the system tag. Runtime-defined helpers use the same naming pattern, but are defined at their initialization points. Registration is not an API whitelist: public use is determined by contracts, examples and call sites. The absence of public/private labels is accepted design, not a need for rebuilding.

Script/include files have names without `fn_`; XEH files, config headers and settings follow established conventions. Naming and comment rules are in [development.md](development.md).

LMF 2.0.0's system names are not backward compatible, and there are no legacy aliases. When transferring, framework, settings, LMF config, mission calls and any Eden calls must be checked together. Active framework helpers/state use `lmf_`; `a2k_*` under framework exists only in commented-out historical medical code. The mission's own `a2k_*` must not be renamed as LMF cleanup.

### Initialization and wait conditions

Start inspection in `description.ext`, `framework/functions.hpp`, `framework/XEH_preInit.sqf` and `framework/XEH_postInit.sqf`. Scheduled work may continue in parallel; start order is not completion order.

1. **Config/functions:** `description.ext` includes `framework/functions.hpp` and `framework/notifications/CfgNotifications.hpp`. CfgFunctions makes registered functions available on each machine; this is not a broadcast.
2. **CBA preInit:** `framework/XEH_preInit.sqf` includes mission settings and color constants, sets the version/admin UIDs, loads AI settings and (when `lmf_playerGear` is enabled) the Player equipment registry synchronously, then BFT helpers/server events. Configuration is created locally on each machine.
3. **Mission event scripts:** `initServer.sqf` and `initPlayerLocal.sqf` contain only comments; no mission-specific player initialization or designator is defined there.
4. **CBA postInit:** LMF uses general XEH `init` on all machine types. The common section starts ACRE, conditional Supply Drop/Forward Deploy and AI NVG, and includes curator/medical events. The server section initializes/publishes warmup and the chat channel, starts markers, tripflare and the warmup deadline. Machines without an interface then exit. The player section waits for `player`, sets `AIThinkOnlyLocal`, registers group notifications/EHs/loadout and starts client modules.
5. **CBA InitPost:** CBA drains the startup InitPost queue after Extended PostInit. `description.ext` routes to the five `lmf_objectSorting_fnc_sort*` functions. AI on `lmf_enemySide` goes to AI init; player gear is initialized explicitly in postInit. Civilian AI is excluded from AI initialization. Vehicles/crates are matched against configured classnames. InitPost for subsequently created objects is deferred to the next frame; code immediately after spawning cannot assume object initialization is complete.
6. **`init.sqf`:** The file contains only a short header and is an available integration point for mission code and temporary tests. Any AI spawning must still be restricted to the server.

Init fragments are textually included and inherit scope/guards; they must not be started separately: `framework/admin/initCuratorEvents.sqf`, `framework/medical/initUnconsciousEvent.sqf`, `framework/warmup/initWarmupState.sqf`, `framework/chat/createChatChannel.sqf`, `framework/chat/initChatMessageHandler.sqf`, `framework/spectator/initSpectatorEvents.sqf` and `framework/respawn/initDeathFeedback.sqf`. The admin diary is included by briefing, marker fragments by marker startup, textures by client postInit.

**Client dependency chain:** The narrative intro sets local `lmf_player_introComplete` → arsenal, object/role actions and `lmf_player_menuInit` can register menus → Mission Info waits for `lmf_player_arsenalInit` only when both `lmf_playerGear` and `lmf_personalArsenal` are enabled and for the entire menu sequence → the info script ends → the intro unit regains simulation. The intro signal does not mean warmup has ended or fade-in is complete. The warmup panel/safety runs in parallel.

`lmf_player_menuInit` registers **BFT → Supply Drop → JIP Teleport → Forward Deploy**. When Supply Drop is enabled, its menu helper registers Supply Drop directly under ACE Self-Interaction. The helpers are defined in module init and called once from the sequence after the required state is available. All four main choices are inherited ACE class self-actions on `CAManBase`. Other mods' ordering is not covered. Equipment menus are separate; spawner/role actions are created on the objects.

**Unresolved:** Waiting for helpers/state has no timeout. A missing helper or replicated state can hold up later menus, fade-in and release. This is a dependency derived from code, not an observed startup failure.

Initialization sources: [BIKI Initialisation Order](https://community.bohemia.net/wiki/Initialisation_Order), [CBA XEH guide](https://github.com/CBATeam/CBA_A3/wiki/Extended-Event-Handlers-%28new%29), [CBA postInit](https://github.com/CBATeam/CBA_A3/blob/master/addons/xeh/fnc_postInit.sqf), [CBA init](https://github.com/CBATeam/CBA_A3/blob/master/addons/xeh/fnc_init.sqf). The CBA source confirms PostInit before InitPost; the actual order with the installed mod set has not been checked at runtime.

### Settings, machines and shared state

| Configuration | Usage and scope |
|---|---|
| `settings/cfg_Mission.sqf` | Included in preInit; global `lmf_camelCase` variables are created locally on each machine. Not a server-replicated settings object. |
| `settings/cfg_AI.sqf` | Included only by `framework/ai/loadSettings.sqf` in preInit. Private values are collected in local `lmf_ai_config`, with reverse classname lookups. Weapon metadata is cached on use in `lmf_ai_weaponCache`. |
| `settings/cfg_Player.sqf` | Included only by `framework/equipment/loadSettings.sqf`, which builds machine-local `lmf_player_config`. Loaded during preInit when `lmf_playerGear` is enabled, or lazily through `lmf_equipment_fnc_getPlayerConfig` when a consumer needs it. |
| `settings/cfg_Briefing.sqf` | Private data is included and formatted by `framework/briefing/createBriefing.sqf`. |
| `CBA_settings.sqf` | Separate mission configuration enabled from `description.ext`; not part of the settings include flow. |

Private includes depend on the consumer's scope; do not replace them with function calls without assessing the contract. Changes to `lmf_camelCase` or `lmf_ai_config` at runtime are local until explicitly synchronized over the network. The AI registry's uppercase HashMap keys are not covered by camelCase renaming.

**Design:** The production environment is dedicated with JIP. `lmf_ai_fnc_isSpawner` uses `isServer`; HC spawning is intentionally disabled because the current volume does not justify the complexity. No HC spawning implementation is retained. Do not assume support for locality transfer of active AI sequences.

| State/system | Writer and distribution |
|---|---|
| `lmf_warmup_isActive` | Initialized on the server; manual termination by an admin also sets/publishes from the client. Not purely server-authoritative. |
| `lmf_chatChannel` | The server creates the channel and publishes its ID. |
| BFT `lmf_bft_state` | The server writes public state on the group; clients draw locally. |
| Supply Drop | The server owns the quota and `lmf_supplyDrop_nextRequest`, publishes the count/deadline; the client sends a request. |
| Forward Deploy | Registry in the server's `lmf_forwardDeploy_registry`; CBA server events receive requests. |
| `lmf_currentRole` | Gear on the unit's owner; the role is published on the unit. |
| Fire support | Server-local battery state, public `lmf_artilleryBusy` for clients/JIP. |

JIP builds the client's briefing, actions and trackers from startup and current state. Respawn is a separate flow; class actions can survive player-object replacement, but parameter binding to the original unit may still limit availability. One-off messages/delivery sequences are not replayed. Object-bound persistent remote execution is used for spawner deletion and BFT object tracking, among other things; deletion and repeated calls must be assessed against the JIP ID contract, without assuming an order between persistent calls.

`description.ext` has no mission-local `CfgRemoteExec`; the effective engine/server/mod policy determines exposure. Clients with an interface enable `AIThinkOnlyLocal` (documented from Arma 3 2.20); remote AI target data therefore cannot be expected to be available there. Hosted servers also have an interface and are covered; dedicated/HC do not.

External calls exist to CBA, ACE/ACEX, ACRE and LAMBS Danger. ZEN is registered only if the function exists; other dependencies have no equivalent general availability guard. Installed versions have not been established.

## Module contracts

### AI init, spawning and garrison

**Files:** `framework/objectSorting/`, `framework/ai/fn_initUnit.sqf`, `framework/ai/fn_initGroundVehicle.sqf`, `framework/ai/fn_initAirVehicle.sqf`, `framework/ai/fn_initWaterVehicle.sqf`, `framework/ai/fn_buildWeaponLoadout.sqf`, `framework/ai/fn_manageNvg.sqf`, `framework/ai/eventHandlers/`, `framework/ai/spawning/`.

- Init continues only for a local unit/vehicle. Classname lookups in the AI registry select role/gear; soldier loadout is built as a Unit Loadout Array and applied together. Attachment/magazine lookups are cached. The hit reaction has a local per-unit cooldown.
- The NVG manager processes existing enemy AI at startup and then at day/night transitions; new AI receives nighttime NVGs in the initial loadout.
- `framework/ai/spawning/spawnDefinitions.sqf` is an include with vehicles/roles, group compositions and private `_typeMaker`. `spawning/` owns group creation; `tasks/` owns registered `task*` entrypoints.
- All AI spawners require Arma 3 2.22+ and scheduled server execution after LMF preInit. Patrol and Garrison are one-shot GROUP-returning functions. Infantry QRF/hunters, Vehicle QRF and Paradrop QRF select one-shot versus managed mode by whether the ticket argument is present. Use `spawn` in both modes: its native promise resolves to the one-shot primary delivery after preparation, or no combined result for managed waves. `waitUntil handle` retrieves the result in scheduled code; `continueWith` receives it in `_this` unscheduled and must keep follow-up work short. A `call` from an existing scheduled script suspends in that scope. Unscheduled calls return null without spawning. Managed calls retain the mission-time startup wait; one-shot calls have no proximity check. ZEN function `remoteExec` already provides a scheduled context but does not transmit promise results back to its caller.
- `requestSpawn` queues one creation request with a native local promise. `processSpawnQueue` is a single on-demand unscheduled CBA callback chain. It creates one soldier and seats it atomically, then schedules the next callback after 0.1 seconds. A `diag_tickTime` deadline measured after actual creation also gates entry, so stale frame-based CBA time or scheduler delays cannot produce catch-up bursts. Queue, active flag and deadline are server-local; the worker stops when empty. No permanent polling worker or general task scheduler is added.
- `spawnGroup` supports only LMF's soldier classname arrays. Inspection of the installed Bohemia `functions_f.pbo` confirms the used BIS path creates with FORM, zero azimuth and no explicit rank/skill/ammo overrides, then sorts via a second group. LMF retains one local group, normalizes side with joinSilent in that same group and selects the highest-rank member (first on ties). Group composition remains selected by spawnDefinitions. `spawnCrew` retains Bohemia's hasDriver check and recursive BIS_fnc_returnVehicleTurrets traversal, including FFV, followed by the existing vehicle rank assignment. Category-specific pruning and commander selection stay in the spawners.
- `lmf_ai_spawning` excludes incomplete groups from Converge and survivor joining until initial setup finishes. The helpers wait for LMF's InitPost routing marker and any deferred gear script. Readiness means the LMF gear attempt finished, not that custom gear was necessarily applied: the existing ten-second weapon-switch timeout can retain original gear. Other mods' asynchronous work and delayed vehicle-light callbacks are not included. Editor unit initialization is unchanged; readiness markers are written only for groups under LMF preparation. Paradrop infantry's existing 1.25 skill adjustment runs after LMF initialization instead of racing the deferred InitPost skill write.
- Pacing covers infantry QRF, Hunters, Patrol, Garrison, vehicle crew/passengers, Paradrop aircraft and payload occupants, and the Supply Drop pilot. Drone `createVehicleCrew` is an intentional atomic exception through the same queue: its engine-managed UAV/UGV crew setup, faction, ranks and seat rules are retained; internal units can share one creation timestamp. The curator ModuleCurator_F is a logic object outside the soldier queue. No editor-placed AI is paced.
- Creation and initialization remain local to the current spawning owner (server for now). Groups are never transferred while partial; queue and promise state are not replicated. Completed groups have no permanent server-local readiness requirement. HC routing/transfer and ownership changes during active insertion are still unsupported. Newly created delivery vehicles are held with simulation disabled during queued preparation and restored before flight/task delivery.
- Each managed spawner calls `lmf_ai_fnc_runWaves` in its current scheduled server scope with a local one-shot operation, tickets, delay, position, radius and poll interval. No registry or persistent JIP execution is used. The controller follows one primary GROUP (no living members) or OBJECT (dead/deleted); a missing, unsupported, null or already-finished initial delivery ends the source. After spawning the final ticket, the controller exits immediately; it waits for delivery completion only while a replacement ticket remains. The spawner synchronously calls the controller, which synchronously calls the one-shot operation, keeping spawner locals alive throughout every replacement wait and spawn. Neither the controller nor that operation is spawned as a closure. Infantry QRF/hunters have no respawn delay; Vehicle/Paradrop QRF retain their configurable 300-second default between deliveries.
- `runWaves` owns proximity through unchanged `lmf_ai_fnc_getPlayerProximityState`. It evaluates actual players through the player's vehicle; `groundClose` ends the source, `airClose` waits, and `airDistance` allows spawning. It checks before every wave, including an explicit one-ticket call, and while waiting to replace a delivery. Ranges are 500 m for infantry/hunters and 1000 m for vehicle/paradrop, with 10-second infantry QRF and 5-second other polling. Proximity is checked again after a respawn delay. Raw one-shot calls bypass this lifecycle.
- Vehicle QRF's primary delivery is CAR/TRUCK infantry GROUP, APC/HELITRANSPORT cargo infantry GROUP, or CARARMED/TANK/HELIATTACK/DRONE vehicle OBJECT. Aircraft/crew cleanup is independent; surviving dismounted crew or an empty transport no longer hold up an unrelated primary delivery.
- Vehicle QRF passes the crew classname to the paced `lmf_ai_fnc_spawnCrew` helper: CARARMED/RIFLEMAN, APC/TANK/CREW, HELITRANSPORT/HELIATTACK/PILOT. DRONE retains atomic `createVehicleCrew` through the shared creation queue. APC/TANK retain only driver, gunner and commander after spawning. Both select a living commander in their local crew group as leader; without a valid commander they retain the existing leader.
- DRONE replaces the UAV category without an alias. `_drones` in cfg_AI.sqf supplies both UAVs and UGVs; duplicates retain random weighting. `spawnVehicleQrf` takes spawn position and vehicle category, with optional trailing tickets and respawn delay. DRONE randomly selects from `_drones` for each spawn; an empty pool does not spawn.
- All drones receive GUARD. Only Air-derived classes receive `flyInHeight` or water-spawn `FLY`. Normal armed/unarmed drones use engine AI. The reverse registry now maps these classes to DRONE; object sorting's existing explicit category lists still exclude drones from normal AI vehicle initialization.
- Air drones with an inherited pylon hardpoint `LXWS_IED_DRONE_PYLON` start `taskUavAttack` on a living detected ground target. The task retains reveal, approximate movement, requested search/approach heights of 50–200 m and drop heights of 20–60 m, the 25 m expected-target-distance check and 30-second drop spacing. It reads currently loaded IED-pylon magazines/ammo with `getAllPylonsInfo` and fires their `pylonWeapon` through `BIS_fnc_fire`. Depletion, death or loss of locality ends the task and removes its movement EnemyDetected handler. Depletion leaves the drone and GUARD waypoint intact; no simulated grenades are created.
- Air drones exposing `FakeDetonator_RF` use `lxRF_fnc_RC40_attack` when available. The first valid EnemyDetected ground target removes the handler before scheduling a wait for engine-on and no ground contact. Death, lost locality or an invalid target cancels the handoff; no second attack is scheduled. RF owns approach and final payload effect. These tasks remain server-local under `isSpawner`; ownership transfer is not supported.
- ZEN passes explicit tickets for infantry QRF/hunters and Vehicle QRF to retain managed one-ticket proximity behavior; Paradrop uses the new trailing-ticket order. Existing broadcast remoteExec execution and UI controls are retained.
- ZEN's Vehicle QRF offers DRONE alongside the other vehicle categories and broadcasts the category-based spawner call. The server randomly selects from `_drones`; Zeus does not expose individual drone classnames. No persistent remote execution or JIP task replay is added.
- `spawnParadropQrf` is server-restricted and takes spawn position, drop zone, flying height, payload, optional tickets and respawn delay. Its one-shot operation prepares the primary infantry GROUP or vehicle OBJECT through the shared creation queue and returns after starting a scheduled flight/drop/retreat/cleanup continuation with explicit state arguments. Failed setup deletes the prepared payload and transport; failed vehicle release deletes the undelivered payload. The shared controller owns tickets/proximity and follows only the payload, independently of aircraft retreat/cleanup. Unit/object drops still delegate to paradrop. The drop zone is a marker, trigger or location; the only supported array is `[0,0,0]` for autonomous mode. Autonomous mode reads the spawn object's direction before position conversion; an array spawn gets a random direction. A fixed drop zone determines the direction toward the zone. ZEN may broadcast the call; `isSpawner` restricts execution.

**Drone evidence/unresolved:** The mission maker reports that WS IED hardpoints identify the payload capability and real firing consumes the four payloads individually. RF HE and tested smoke variants reportedly work with the native attack function, but calling it before takeoff moves a grounded drone unnaturally. The RF documentation describes HE; smoke support is based on those local runtime tests. The mission maker reports successful in-game testing of the integrated DRONE system. The revised IED flight heights await in-game evaluation; dedicated-server/JIP coverage of the reported tests was not specified. BIKI community notes warn that `isTouchingGround` has surface/remote-object limitations; checking the local drone does not establish reliable detection of every remote target.

**Garrison design and implementation:** ACE Garrison places infantry in buildings after the existing nearby gunner-seat allocation. Initial and contact stances use a 10-meter vertical GEOM trace from eye position: a hit whose parent object is a Building selects standing/kneeling, otherwise kneeling/prone. This also applies to CBA Building Positions; ACE garrison state determines eligibility for contact reactions, not indoor/outdoor classification. One group EnemyDetected handler randomizes stances only for living, local, uncaptured soldiers on foot who remain ACE-garrisoned with PATH disabled. Each such soldier within 75 meters of the detected target has a 10% release chance. `ace_ai_fnc_unGarrison` clears ACE bookkeeping and restores PATH/FSM; LMF restores AUTO stance and adds no relocation orders. Released soldiers are no longer stance-controlled. There are no garrison-specific Hit/FiredNear reactions, additional cover calculations, casualty probabilities or surrender routines. The shared AI initialization hit reaction remains. Last-survivor reassignment and Dynamic Simulation remain.

**Infantry QRF and Patrol:** QRF uses a GUARD waypoint without contact-driven waypoint relocation. Patrol retains its radius, presets, formation, land/water safe-position fallback and four MOVE waypoints plus CYCLE. Ground contact on land replaces that route with GUARD, AWARE/FULL and a QRF group name, then removes only the patrol-to-QRF handler. The QRF name contains no Patrol keyword. The group never automatically returns to patrol. There are no animation-speed, CombatModeChanged or CommandChanged overrides, or delayed patrol behavior writes.

**Vehicle QRF:** All eight categories share vehicle/group/GUARD setup while preserving crew classes, names, passenger compositions, separate APC crew and infantry, and primary delivery returns. CAR/TRUCK/APC disable automatic combat unloading and use one-shot LMF ground-contact dismount within 500 meters with GUARD retargeting. The infantry group retains a server-local transport reference for leaveVehicle, so dismount removes the original vehicle assignment even if its leader is already on foot. Transport infantry shares Infantry QRF's DIAMOND/FULL/RED, ForceOff/IR-off defaults and permanent 75-meter light reaction, gated until the leader is on foot. Its UnitKilled reaction reassigns a lone survivor only when on foot; mounted casualties do not reassign vehicle occupants. Pure vehicle crews have no UnitKilled reassignment. Ground-vehicle GetOut no longer empties the weapon or forces suppression, as a gameplay test; flip handling remains and air initialization is unchanged.

**Paradrop vehicle QRF:** CAR/CARARMED/TRUCK/APC/TANK use the corresponding Vehicle QRF compositions and crew classes. CAR/TRUCK share one infantry group (normally 6/12 units including the driver); APC has a separate crew and normally eight infantry; CARARMED/TANK have crew only. Actual seats cap delivered infantry, as in Vehicle QRF. APC/TANK use the same crew pruning and commander leadership. Direct classnames use the existing `VEHICLE_BY_CLASS` category when it is one of these five; otherwise the paced crew helper fills crew seats with configured CREW units, selects a valid local commander and adds no infantry or category-specific pruning. Class inheritance does not determine an LMF category.

Vehicle-payload crew and passengers are prepared through the queue before flight, hidden globally with simulation and damage disabled until release. This required timing change prevents queue backlog from outlasting descent. They retain planned driver/turret/ANY seats; release and seating run together unscheduled, with APC/TANK crew pruning before passenger seating. Failed preparation, aircraft loss or failed release removes staged occupants and empty groups. No soldier creation happens during descent. The aircraft is held during preparation; initial flight orders and departure begin only once preparation is complete. CARELESS/BLUE, disabled FSM/AUTOCOMBAT and blocked combat unloading hold combat reactions until the existing landing continuation detects detachment plus ground contact or height below 0.5 meters, then waits one second. It restores AWARE/FSM/AUTOCOMBAT and GUARD for both groups. Automatic combat unloading remains disabled after landing; the LMF dismount handler uses the stored transport reference, independently of the leader's current vehicle. Vehicle-carried infantry then receives Vehicle QRF's formation, combat mode, dismount, light/IR and on-foot survivor handlers. Immediately before ACE vehicle release, the server-local transport aircraft has its local PhysX/geometry collision flag disabled. A single CBA callback restores the original flag on the same machine after three seconds; failed release also restores it immediately. Payload release position, forward velocity, pitch/bank, aircraft retreat, shared parachute/landing cleanup and infantry-only drops retain their existing flow. The collision command requires Arma 3 2.18; LMF spawning now requires 2.22 for native promises. Roadway LOD collisions remain, and the brief loss of aircraft collision with other objects/terrain is intentional; three seconds is a test value, not an engine guarantee of separation. Paradrop still returns/tracks the vehicle OBJECT for every vehicle payload: CAR/TRUCK/APC waves therefore follow vehicle destruction, unlike Vehicle QRF's infantry completion. No JIP replay or extra tracking is added; server ownership throughout insertion is required.

### AI groups, hunters and boats

**Files:** `framework/ai/groups/`, `framework/ai/tasks/fn_taskHunt.sqf`, `framework/ai/tasks/fn_taskConverge.sqf`, `framework/ai/tasks/fn_taskPatrol.sqf`, `framework/ai/boats/`.

`assignCallsign` is server-authoritative, with a local counter per reserved LMF prefix and `setGroupIdGlobal`. An invalid group, empty prefix or non-server call returns an empty string. Names are sequential within the helper; manually named groups are not checked for collisions. Lone supported LMF survivors are ungarrisoned and join the nearest eligible group, otherwise GUARD. The GUARD fallback removes old task waypoints while preserving completed waypoint 0, resets individual movement with `doFollow`, and explicitly activates GUARD without a temporary CBA MOVE waypoint. `taskConverge` requires a local group; `taskPatrol` selects water positions when the leader is in a Ship. Failed MOVE and CYCLE safe-position searches fall back to the patrol target position for both land and water; successful searches retain their existing distance and terrain constraints.

**Hunters:** `taskHunt` runs scheduled on the group owner, updates immediately and then every 13–17 seconds and individually issues doMove to the nearest living actual non-civilian player's getPosATL within the leader's horizontal radius. Headless clients and airborne aircraft are excluded; foot targets do not require isTouchingGround, including upper floors. FULL speed and no fleeing prioritize movement. Arma AUTOCOMBAT and FSM remain enabled; only startup sets AWARE, so the hunt does not repeatedly overwrite combat behavior. A UnitKilled event leaving at most one living soldier terminates the stored hunt script before clearing the hunt flags and restoring attack, fleeing, AWARE/NORMAL and RED. The local survivor becomes leader, resets stance/speed and individual movement, and calls reassignSurvivor directly without a delayed task handoff; it joins an eligible friendly group or receives the existing GUARD fallback. A group initially spawned with one soldier still hunts until its casualty event. Locality loss ends the loop without transferring it. Managed-wave spawn protection remains 500 meters; raw one-shot calls bypass proximity. Hunter groups are not join recipients.

**Convergence:** Public `call` returns before all orders are applied. One scheduled worker per invocation spaces groups by approximately 0.1 seconds. Per-group request versions make newer requests supersede older pending orders. The worker rechecks group-name selection, locality, side, living/local leader, static-weapon exclusion and transport eligibility before each atomic cancellation/assignment. Groups flagged as spawning are excluded both at selection and application. For each accepted group, cancellation and new orders still run together unscheduled. Converge terminates the stored hunter script, restores attack/fleeing and clears both group and individual LAMBS hunt flags, removes only the stored patrol-to-QRF handler, and ungarrisons ACE-bound infantry. doFollow replaces outstanding individual movement before the new GUARD waypoint. `lmf_taskConverge_active` remains a temporary boat reservation, never a permanent land-group lock; subsequent land convergence calls can retask the same group.

A boat hunter with a target reserves a landing before `landBoatGroup`; hunt orders/GUARD are withheld during landing. After the flag is released and the leader is on foot, landing waypoints are deleted once at the next hunt update, even without a target. Without a target, doMove is issued to the soldiers' own positions; GUARD is not restored after disembarkation. Groups that have not landed retain the GUARD fallback. A failed shoreline search can be retried; a stuck landing has no new timeout.

**Boat flow:** `spawnBoatForGroup` is used by patrol, infantry QRF and hunters for water spawns and calls `initBoatAssault`. Landing from EnemyDetected, converge and hunt reserves `lmf_taskConverge_active` locally before calling the helper. Checking/reservation happens together unscheduled; direct calls to internal `landBoatGroup` must be reserved by the caller. The flag is held through random disembarkation delays until no living group members remain in the boat or the boat is deleted. A deleted group exits without writing state; a failed shoreline search releases the flag and assigns GUARD at the boat.

`findShorelinePosition` searches from 500 meters around the target, doubles up to the caller's limit and uses the first match as the center of an independent 500-meter dispersion search. If dispersion fails, the first match is used; if there is no first match, `[]` is returned. Dispersion can extend beyond the caller's radius. The result is shifted 10 meters toward the boat, height 0. The search does not guarantee the nearest shore, a continuous coastline, a land connection or a navigable approach; boats do not share reservations/landing sites.

`initBoatAssault` also has a five-second local GUARD check: ground contact and absolute speed below 20 km/h trigger reserved `dismountBoatGroup` without a new shoreline search/waypoint change. Other waypoint types and floating boats are not covered. The check ends on triggering, no survivors in the original boat, a destroyed/deleted boat/group or lost locality. Shared disembarkation retains leaveVehicle, AWARE, random delay and smoke. QRF retains GUARD; hunt clears its own landing waypoints.

The current shoreline search/GUARD fix and autonomous disembarkation have not been verified in-game; multiple boats, the last survivor and dedicated/JIP remain unresolved. | Entry | Contents |
| --- | --- |

| `GRENADES` | Pools under `FRAG`, `SMOKE`, `SMOKE_COLOR`. |
| `ITEMS` | Scalar classnames under `BINOCULAR`, `NVG`, `NVG_PILOT`. |

Flare gun scalar weapon/ammunition settings are wrapped in one-element registry arrays and extracted as scalars by `giveWeapon`. ### Respawn, spectator, medical and hit effects

Chat selects CBA level all only on a fixed admin's own client, otherwise admin with CBA's login/logout check. heal/goto/bring/respawn have only this local authorization; start/victory/defeat/respawnwave/performance delegate to the LMF admin layer's own checks. `/w` and `/zeus` use a non-persistent global CBA event, with a receiver only on interface machines. ACRE channel names are initialized on all machines; `lmf_radio_fnc_hasLongRangeRadio` is used from server and client.

`#bring` on foot teleports as before. From a vehicle, the helper targets the target player's client with remoteExecCall. The same living admin vehicle is required; only an ordinary cargo seat is selected, not driver/turret/FFV. A full vehicle is rejected before movement; someone already aboard remains seated. Other clients' concurrent seat use is not reserved. The respawn-wave dialog uses the active ACE Spectator display as parent; the player selection is retrieved only on OK before a 30-second respawn time is sent. Cancel sends nothing.

**Unresolved:** Admin functions check the supplied unit, but its relationship to any remote sender has not been security-verified. The effective remote-exec policy/server/mod setup determines actual exposure. Access without login, login/logout, respawn/JIP and bring seat competition have not been verified in-game.

### Fire support

**File:** `framework/ai/fireSupport/fn_fireSupportAtTarget.sqf`. Scheduled/server-restricted, for server-local AI with MK41 VLS or an artillery computer. The fourth argument `_playerRequested` defaults to false; only player-requested strikes notify existing LRR recipients and receive VLS BFT. The development mission now contains no designator or autonomous init call to the function. Player-controlled/remote turrets and ownership changes have not been established as supported.

The busy lock is acquired together in isNil; battery/target are validated again after preparation. Public `lmf_artilleryBusy` provides client/JIP availability; server-local `lmf_fireSupportState` stores filter/count/times and is removed with the Fired handler before cooldown. Artillery selects a magazine dynamically and counts only the selected magazine; VLS filters weapon_VLS_01 and its associated magazines.

Artillery is released ten seconds after the last shot of a full or observed-ended partial salvo; VLS 60 seconds after the first confirmed launch. Preparation is additional; flight time does not extend the lock. VLS has a separate Splash observer, maximum 300 seconds, without access to the lock. Splash only means the projectile is gone/not alive, not a confirmed hit. Artillery has no flight tracking/Splash.

Shot/Missile away/Round away occurs on the first shot; multi-round artillery gets the actual count in Rounds complete. Battery standing by occurs on release only for a living/local battery. Launch failure releases as soon as the failure is confirmed. Time limits are eight seconds for VLS, 30 for artillery and `30 max (_rounds * 15)` for the salvo. Timeout means missing confirmation, does not cancel engine orders and does not automatically send the remaining salvo. Messages are not replayed; VLS object tracking has JIP.

**Unresolved:** Late firing after timeout, unitReady with a partial salvo, concurrent requests, filter/cooldown/message order and VLS BFT/JIP have not been verified in-game. The earlier BIKI fireAtTarget page lacked locality/effect labels; a server-local implementation alone is not runtime evidence.
